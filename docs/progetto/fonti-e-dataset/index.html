Fonti e dataset: da dove viene ogni numero

Versione 0.2 del 2026-11-20 · ticket #81 · registro delle revisioni

1. Perché

Ogni numero pubblicato deve potersi rifare da un clone pulito del repository (AGENTS.md § 5). Finora lo avevamo dimostrato per il mirror ANAC e per quattro file di lavoro (RIPRODURRE.md). Ma le verifiche leggono anche BDAP, SIOPE, Indice PA, TED, GLEIF, il censimento MEF delle partecipazioni, Developers Italia, pagine raccolte dal vivo, e tabelle che curiamo noi. Questa pagina le elenca tutte, con lo stato di ciascuna, ed è rigenerata da python3 tools/fonti.py pagina.

Esempio: la vista sulle società ICT pubbliche dipende dal censimento MEF (mirror, sha256), dai CIG e dagli aggiudicatari ANAC (mirror), da un file di lavoro con i codici fiscali per CIG (congelato in git con sha256) e da due tabelle curate a mano (siti e soci, con la fonte di ogni riga).

2. Come si legge

Ogni ingresso di uno strumento è di uno di questi tipi:

  • mirror: file scaricato dalla fonte e conservato nell’archivio append-only, indirizzato per sha256; si ripristina dall’archivio;
  • lavoro: file intermedio in lavoro/ (fuori da git). Deve essere congelato (copia in git o nell’archivio con sha256), oppure essere un intermedio che un comando rifà da ingressi già congelati;
  • git: tabelle curate, esiti e classificazioni versionati;
  • rete: letto dal vivo (es. API di GitHub, DNS); le risposte usate si archiviano con sha256 dove possibile;
  • modello: esiti di un modello linguistico, già versionati: non si rigenerano, si rileggono.

Modi di congelare un file di lavoro: git (copia compressa in dati/ingressi/), archivio (blob con sha256), archivio-tar (cartella intera in un tar deterministico, più l’elenco degli sha256 di ogni file in git), impronta (solo l’elenco degli sha256, per file enormi che si rifanno dal mirror: lavoro/cig_completo, 11 GB).

3. Sintesi della verifica

Verifica del 2026-11-20: 92 strumenti esaminati, ingressi per tipo git 135, lavoro 84, mirror 54, modello 5, rete 6; 17 host del mirror; 22 ingressi di lavoro/ congelati; non registrati: 0; host senza acquisizioni: 0. Esito: ok.

Prova da clone pulito del 20/11/2026 [V]

tools/verifiche/clone_pulito_fonti.sh (esito in esiti/2026-11-20/fonti/clone-pulito.txt): clone del repository al commit 753d4158 con l’archivio del server in sola lettura; ripristinati tutti i 21 ingressi congelati; lavoro/cig_completo (235 file, 11 GB) rigenerato dal mirror ANAC in 7 minuti e identico, file per file, alle impronte; registro delle fonti «ok»; catena delle società ICT pubbliche e del cloud in proprio rifatta: censimento, codici fiscali per CIG (rigenerati dal mirror e identici a quelli congelati), livello DC, tabella unica, stati finali e vista identici a quelli pubblicati. Unica differenza trovata: lo sha256 del file compresso del livello DC, perché gzip vi scriveva l’ora; corretto (compressione senza data in datacenter_proprio.py e imbuto_spostamenti.py).

Attenzione: il raffinamento L4 è ancora in corso e aggiunge esiti, quindi la tabella unica rifatta dopo un nuovo esito L4 può cambiare. Ogni pubblicazione cita gli sha256 degli ingressi (riepilogo.json della tabella unica) e tools/ingressi_lavoro.py congela lavoro/imbuto/stati-finali.csv.gz riallinea il registro.

8. Limiti

  • L’inventario degli ingressi è statico (lettura del codice, config/fonti-verifiche.yaml): un percorso costruito a runtime può sfuggire. Il controllo dinamico è la prova da clone pulito (tools/verifiche/ripetibilita.sh).
  • Le raccolte dal vivo (sezioni di Amministrazione trasparente, atti L4, dataset L. 190) non si rifanno identiche: si conserva lo stato raccolto e le pagine scaricate.
  • lavoro/cig_delta non ha uno strumento che lo produca (estrazione a mano dei delta ANAC): congelato, origine da documentare.
